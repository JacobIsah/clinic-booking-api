# Deploying

Two free accounts, no card, nothing to pay. Render runs the app, Neon holds the
database.

Render's own free Postgres is deleted after 30 days, which is why the database
lives on Neon instead — its free database has no expiry, so bookings made today
are still there next month.

## 1. Accounts

| Account | What for | Sign up |
| --- | --- | --- |
| GitHub | holds the code Render deploys from | <https://github.com/signup> |
| Neon | the Postgres database | <https://neon.tech> |
| Render | runs the app on HTTPS | <https://render.com> |

Sign in to Neon and Render with the **Continue with GitHub** button — then there
are no extra passwords and Render can see the repository straight away.

## 2. Neon — create the database

1. Sign in, then **New Project**.
2. Name it `clinic-booking`, leave the Postgres version as the default, and pick
   the region closest to you.
3. On the project page, open **Connection string** and copy the
   **pooled** connection string. It looks like:

   ```
   postgresql://USER:PASSWORD@ep-something-pooler.REGION.aws.neon.tech/neondb?sslmode=require
   ```

   Keep this. It is the `DATABASE_URL`.

## 3. GitHub — push the code

From this project folder:

```bash
git remote add origin https://github.com/YOUR-USERNAME/clinic-booking-api.git
git push -u origin main
```

Create the repository first at <https://github.com/new> (private is fine —
Render can read your private repos once connected).

## 4. Render — run the app

1. **New** → **Web Service** → connect the GitHub repository.
2. Render reads `render.yaml`, so the build and start commands are already set.
   Confirm:
   - Runtime: **Python 3**
   - Build command: `./build.sh`
   - Start command: `gunicorn config.wsgi:application --workers 3 --threads 2 --timeout 60 --bind 0.0.0.0:$PORT`
   - Instance type: **Free**
3. Add the two environment variables Render cannot guess:

   | Key | Value |
   | --- | --- |
   | `DATABASE_URL` | the Neon pooled connection string from step 2 |
   | `API_KEYS` | the key graders will send in `X-API-Key` |

   `DJANGO_SECRET_KEY` is generated by Render, and `DJANGO_DEBUG` is already `0`.

4. **Create Web Service**. The build runs `collectstatic` and `migrate`, so the
   tables are created on the first deploy.

The service comes up at `https://<name>.onrender.com`. The web page is at `/`
and the API is at the same base.

## 5. Check it

```bash
BASE=https://your-service.onrender.com
KEY=your-api-key

# no key -> 401
curl -s -o /dev/null -w '%{http_code}\n' $BASE/slots

# load some slots
curl -s -X POST $BASE/reset -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"slots":[{"id":"s1","provider":"Dr Ade","start":"2026-12-10T09:00:00Z","end":"2026-12-10T09:30:00Z"}]}'

# book one
curl -s -X POST $BASE/bookings -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"slot_id":"s1","name":"Ada Obi","email":"ada@example.com"}'
```

## Keeping it awake

A free Render service sleeps after 15 minutes with no traffic, and the next
request has to wait for it to start again — about 50 seconds, long enough for a
grader's request to time out.

`.github/workflows/keepalive.yml` pings `/healthz` every 10 minutes from GitHub
Actions, which keeps the service warm for free. It starts working as soon as the
repository is on GitHub; set the `BASE_URL` repository variable to the Render URL
(**Settings** → **Secrets and variables** → **Actions** → **Variables**).
